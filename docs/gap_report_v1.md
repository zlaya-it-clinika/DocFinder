# Отчёт v1: DocSearch против ТЗ ПСБ «Юридический ассистент»

Составлен до получения вводных данных ПСБ (регламент, база знаний, пример сабмита).

Итог: DocSearch переиспользуем частично. Чат, источники под ответом, редакции документов, двухшаговый RAG и Python-прототип подходят как основа. Но проект сделан под другой домен (делопроизводство/ДОУ), под локальную Vikhr-Nemo через Ollama и не имеет обязательной точки входа `solution.py`, от которой зависит 70% оценки и допуск к экспертизе.

Проверено: ТЗ целиком, README всех модулей, compose, Dockerfile, `.env.example`, цепочка ответа (`live.go`, `live_reply.go`, `reply.go`, `texts.go`), нарезка (`chunk.go`), SQL поиска, миграции, компонент источников в вебе, прототип `RAG/`. Сборку и тесты не запускал.

## 2. Требования к ответам

| ID | Статус | Найдено в коде | Как доделать |
|---|---|---|---|
| R-01 | частично | `chunk.go` распознаёт только «раздел», «пункт», «приложение», `N.N`. Без структуры — 800 символов | Уровни «Глава», «Статья N», «часть», «пункт N)», пункты договора. Метаданные документа: тип, номер, дата, `effective_from/to`, контрагент, `parent_document_id` |
| R-02 | частично | Только косинус, топ-5. Нет полнотекстового поиска и реранкера. При близких скорах двух документов — переспрос | Гибрид `tsvector('russian')` + вектор + RRF, опционально Qwen3 Reranker. Топ-8–12, многодокументный ответ — норма |
| R-03, C-07 | частично | Цитаты есть, но в тексте ответа ссылок нет | Маркеры `[n]` в тексте, проверка в коде, поле «статья» в цитате |
