## Уточнения Q&A: обязательные правила

- Главный сценарий — поиск документа и точного положения в предоставленной базе. Пользователь — сотрудник банка с юридическим образованием или без него; права доступа к документам и формат ответа для всех одинаковые. Ускорение общения с клиентом вторично.
- База на публичной и приватной проверке одинакова. Её нельзя дополнять или обогащать внешними источниками. Разрешены предварительное разбиение документов и служебные индексы в ZIP, но вспомогательные файлы должны лежать в подпапке, не в корне.
- Ответ опирается только на локальные документы: в тексте нужны название документа и пункт/статья; короткая цитата — когда формулировка влияет на вывод. Если вывод следует из двух пунктов, показать цепочку и сослаться на оба. Закон выше внутреннего регламента. При несовместимых одновременно действующих регламентах — уточнение.
- Для проверки договора брать редакцию, действовавшую на дату заключения. Если дата редакции не указана, брать действующую и прямо называть её дату. Неоднозначный вопрос без истории допускает уточнение или несколько вероятных вариантов с указанием различий.
- Подтверждённый частичный ответ лучше полного отказа. При нехватке данных перечислять конкретные недостающие документы, акты или сведения. Вопрос вне юридической/документной компетенции — обоснованный отказ.
- Ориентир длины — около 150 слов, при необходимости больше; жёсткий предел 10 000 символов. Судья длину не оценивает. Общая оценка: 70% онлайн LLM-судья и 30% экспертная проверка технических решений и владения ими.
- Прогон всех вопросов ограничен 20 минутами, ресурсы — 8 CPU/16 ГБ RAM. Дополнительные зависимости и собственные модели запрещены; только версии из платформенного `requirements.txt` и API моделей из sample submission. Доступен Qwen3 reranker. Время отдельного ответа балл судьи не меняет.
- Для демонстрации достаточно локального Docker и веб-чата. Внешних сервисов, включая КонсультантПлюс, в среде решения нет. Публичное развёртывание интерфейса — дополнительный плюс, не обязательство.

## Как продолжить работу (для следующего агента)

- Python: `py -3.12`. venv: `DocSearch/engine/.venv` (httpx 0.28.1, numpy 2.2.6). Пересоздать: `py -3.12 -m venv .venv; .venv\Scripts\python -m pip install -r requirements.txt` (pip долгий, запускать в фоне через Start-Process).
- Все тесты (из `DocSearch/engine`): `cmd /c ".venv\Scripts\python -m unittest discover -s tests -t . > test_out.txt 2>&1"`, затем читать `test_out.txt`. Вывод через файл: PowerShell портит кириллицу в stderr.
- Эксперименты из рабочего `engine/` собирать через `.venv\Scripts\python build_submission.py --out dist/_history/submission_experiment.zip`. Рабочий каталог содержит экспериментальные модули. Для воспроизведения выбранного пакета использовать исходники из `engine/dist/_history/ab_grounding/submission_engine/` или из самого `engine/dist/submission.zip`.
- Прогон как на платформе: в пустой папке `DATA_DIR=<engine>\tests\data\demo`, `python <engine>\solution.py`. Данные `tests/data/demo` создаются тестами из `../файлы`.
- Отладка: `debug_parse.py <база> [doc_id]`, `debug_search.py <база> <questions.csv>`, `debug_retrieve.py <база> <questions.csv> [id]`, `debug_answer.py <база> <questions.csv> <id,id> [--prompt]` (против фейковой модели).
- С реальной моделью: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `EMB_MODEL=baai/bge-m3`, опционально `RERANKER_MODEL`; запустить `solution.py`.
- Локальный гибридный тест: Ollama `bge-m3` установлен на ПК, API `http://127.0.0.1:11434/v1`. Для разделения провайдеров задать `EMBEDDER_BASE_URL=http://127.0.0.1:11434/v1` и `EMB_MODEL=bge-m3`; `LLM_BASE_URL/LLM_MODEL/LLM_API_KEY` остаются у DeepSeek. Ключ генерации на локальный API не отправляется. Запуск из `engine/`: `.venv\Scripts\python eval_embeddings.py --kb tests/data/demo/knowledge-base.zip --cases tests/challenge_cases.csv --cache dist/bge-m3-vectors.npz`. Модель Ollama нужна только локальным тестам и в ZIP не включается.

## Известные ограничения и решения

- Без модели ответ — дословная цитата лучшего пункта (kind `partial`) или отказ. Безопасно, но судья оценит такие ответы ниже baseline.
- `MIN_COVERAGE=0.25`, `OUT_OF_SCOPE_COVERAGE=0.35` и `RELATIVE_CUTOFF=0.45` проверены на 50 локальных сценариях с BM25; влияние bge-m3 и платформенного реранкера остаётся проверить сабмитом.
- «Вне компетенции» — правилом (низкое покрытие и нет юридических слов), без вызова модели.
- `TOP_K`/`RERANKER_TOP_N` платформы ниже 6 поднимаются до 6: у нас фрагменты-пункты, а не документы.
- Docker Desktop отсутствует в среде проверки; перед боевым развёртыванием остаётся выполнить `docker compose up -d --build` на машине с Docker.
